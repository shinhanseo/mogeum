# 메뉴판 사진 준비 중 취소·부분 실패

사진을 복사하던 중 취소/화면 닫기 후 도착한 파일이 임시 저장에 포함되지 않은 채 남을 수 있었다. 재촬영 직후 다시 진입하면 같은 revision 경로를 동시에 준비할 수도 있었다.

사진 준비 queue를 계정별로 공유해 화면 재마운트까지 직렬화한다. 유효한 배치만 한 번에 화면에 반영하며 취소·부분 실패한 배치는 이 작업이 준비한 미반영 사진만 정리한다. 정리까지 끝나야 다음 배치가 같은 경로를 재사용한다. 이미 반영한 사진·기존 사진·다른 계정 파일은 이 queue가 삭제하지 않는다. metadata 저장 실패 시에는 기존 복구 경로를 유지하고 화면에서 사용하는 사진을 지우지 않는다. 파일 삭제 자체의 실패는 best effort이며 다음 배치를 영구 차단하지 않는다.

기존 Figma UI/문구는 변경하지 않았다. `/dev/menu?runId=<영문숫자_- 최대40자>`는 개발 전용의 분리된 합성 메뉴판 저장 공간을 제공한다. `MenuFlow`를 run별 key로 분리하며 운영 Auth·DB·사진을 사용하지 않는다.

## 검증 · 2026-10-24

- npm run check: 타입·린트·질문 계약, 전체257개 중251 pass·환경6 skip.
- 취소 후 native copy 완료→정리 완료 전 재마운트의 동일 경로 쓰기 대기, 여러 장 중간 실패 정리/기존 사진 보존, 반영한 사진 보존, 정리 실패 후 queue 복구, 계정별 독립, 대기 중 취소된 작업이 copy를 시작하지 않음을 지연 port 테스트로 확인했다.
- iOS Simulator와 Android Emulator에서 run별 합성 메뉴판 사진 추가→다시 찍기→실제 Vision/ML Kit OCR 4줄·사진1/1 읽음 확인. 각 replacement.png 참고. 해당 fixture 폴더에는 revision2 JPEG만 남았다.
- 위 native 검증은 이미지 조작·파일 복사·교체·OCR의 정상 경로다. 취소가 파일 복사 도중 발생하는 세밀한 경합을 native에서 강제로 재현했다는 뜻은 아니며 지연 테스트와 구분한다. 실제 카메라 촬영/사용자 사진/서버 개인화도 이 개발 fixture 검증의 범위가 아니다.

검증 초기에 기존 iOS `menu-ocr-fixture` 초안이 복구 실패했다. 해당 원본은 덮어쓰거나 삭제하지 않았고 새 run 공간으로 정상 경로를 확인했다. 이 이전 초안의 파일 경로/복구 원인은 후속 조사 대상이다.
