# 술장 관리·전체 삭제 · #167

기존 삭제는 상세 → 작은 ‘수정’ → 편집 화면 맨 아래 ‘기록 삭제’에 있었고 한 날짜의 경험만 삭제했다. 술장 카드의 ⋯ 버튼/길게 누르기에서 관리 화면을 열고, 날짜별 기록 수정·삭제와 술 전체 삭제를 구분한다. 상세 링크도 ‘수정·삭제’로 표시한다. 관리 화면은 기존 ScreenHeader·Button·토큰을 사용한 새 상태이며 기존 Figma 프레임과 픽셀 단위 일치를 주장하지 않는다.

전체 삭제는 서버에서 읽은 연결 기록 수를 표시하고, 사진·노트도 삭제됨과 되돌릴 수 없음을 별도 확인한다. 최신 기록 ID를 임의로 반복 삭제하는 클라이언트 루프를 사용하지 않는다.

## 서버 계약

- `cellar_deletion_context(p_entry_id)`: 인증된 소유자의 이름/전체 기록 수/최근 기록 ID/snapshot. 삭제가 완료된 본인 항목은 `deleted:true`.
- `delete_cellar_entry(p_entry_id,p_expected_snapshot)`: 서버가 auth.uid로 소유권 확인, 계정 삭제 동결 검사, 항목/경험 행 잠금 후 snapshot 비교. 기록 추가·수정이 있으면 40001로 재확인을 요구한다.
- 전체 경험과 술장 항목을 한 트랜잭션으로 삭제한다. 기존 기록 tombstone·사진 삭제 작업 큐·노트/질문 cascade를 유지한다. 타 주종/다른 항목/다른 사용자는 삭제하지 않는다.
- private 삭제 영수증에는 본인 항목 ID·삭제된 기록 ID·시각만 남긴다. 응답 유실 뒤 같은 요청 재시도는 같은 ID를 반환한다. 노트·사진 내용은 보관하지 않는다. Auth 삭제 때 영수증도 cascade 삭제한다.
- 사진 바이너리는 기존 durable 삭제 작업 큐로 정리한다. 현재 기기 파생 이미지 정리와 Storage 삭제 실패는 다음 술장 진입에서 재시도한다. 네트워크 실패 뒤 서버의 삭제 완료를 실패로 되돌리지 않는다.

## 검증 · 2026-10-27

- PGlite 실제 마이그레이션: 소유권, 기록 추가/수정 충돌, 응답 유실 재시도, 사진 큐, 삭제 기록 생성 재시도 차단.
- 별도로 생성한 격리 PostgreSQL DB + Supabase 플랫폼 fixture에서 DB suite 31/31 통과. 다른 연결의 새 경험 추가 트랜잭션이 진행 중일 때 과거 확인으로 삭제를 시도하면 대기 후 40001, 새 기록 포함 2개 모두 보존됨. 기존 로컬 사용자의 데이터베이스는 초기화하지 않았다.
- 로컬 Supabase 실제 Auth/REST/Storage: 임시 계정 2개, 실제 fixture JPEG 업로드, 그룹 삭제·재시도·타 계정 보존·바이너리 삭제 성공. 임시 계정과 파일만 정리했다. 사용자 실제 기록/사진은 삭제하지 않았다.
- 작은 iPhone Simulator: 카드 ⋯ 진입, 확인 화면의 기록 수/경고, 취소·합성 완료 상태 확인. 개발 서버에는 추가 마이그레이션 20261027010000 하나만 적용했다.
- 설치된 기기의 새 삭제 UI 업데이트는 코드 구현/DB 배포와 구분해서 기록한다.
