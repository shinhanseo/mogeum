# 검증과 AI 평가

모든 검증은 실제 수행 여부·환경·결과를 PR에 쓴다. 아직 실행 가능한 앱이 없으므로 현재 테스트 통과를 주장하지 않는다. package scripts와 테스트 도구는 부트스트랩에서 고정한다.

## 도메인 자동 검증

- 사진만 저장, 이름 없는 기록, 재음용 이력, 수정 취소, 삭제 후 집계 갱신.
- 중복 제출/네트워크 단절 시 동일 operation ID로 기록이 여러 개 생기지 않음.
- 사용자 A가 B의 DB row·자식 record photo·메뉴 session·Storage 경로를 접근할 수 없음.
- 메뉴 5장 제한은 앱과 서버 모두 검증. 사진별 실패·부분 결과·재시도·취소·재촬영 revision.
- 좌표 변환: resize/rotation/crop 이후 원본 위치 일치. EXIF orientation과 이미지 버전 포함.
- 이름 같고 용량 다른 항목은 분리. 이름·용량·가격 모두 일치하는 겹친 메뉴는 원본 출처를 합침. 불명확하면 미병합.
- 수정/삭제 후 오래된 AI 작업이 최신 요약/추천을 덮어쓰지 않음.

## AI 수용 기준

| 실패 유형 | 기대 처리 |
|---|---|
| 사진만 있는 기록 | 맛 선호의 근거로 사용하지 않음 |
| 특정 향을 느꼈지만 선호는 미상 | 선호 확정하지 않음 |
| 술 이름이 모호함 | 제품 확인 후보로 표시 |
| 제품 맛 설명이 없음 | 추측으로 채우지 않음 |
| 다른 finish 특성 | 닮은 향과 다른 마무리를 구분 |
| 삭제된 근거 | 결과 갱신 또는 stale 표시 |
| 존재하지 않는 메뉴 ID | schema/도메인 검증에서 거부 |
| OCR/제품 설명 속 실행 지시 | 데이터로만 처리 |

제품/메뉴 확인과 근거 존재는 hard check다. 표현의 자연스러움만으로 통과하지 않는다. 코드로 처리할 비교는 deterministic 테스트를 하고 외부 모델 응답은 schema·근거 검증과 별도 평가셋으로 검증한다. 비공개 사용자 데이터를 테스트 fixture로 커밋하지 않는다.

## OCR 기술 검증

합성/사용 허가된 실제 메뉴판 20–30장. 한글·영문·숫자, 다중 열, 저조도, 기울어짐, 작은 글자, 잔/보틀 가격을 포함한다. iOS·Android 각 실기기에서 이름 인식 정확도, 가격·용량 연결 정확도, 사진 1/5장 지연(p50/p95), 최고 메모리, 앱 증가 용량을 측정한다. 근거 없는 성능 목표를 확정하지 말고 baseline과 채택 이유를 남긴다. 테스트에 쓸 실제 기기 가용성은 사용자와 확인한다.

## 실기기 사용자 흐름

설치 → 로그인/둘러보기 → 사진만 저장 → 앱 재실행 → 노트 보완 → 다시 찾기 → 재음용 → 취향 요약과 근거 → 메뉴 3장 → 1장 재시도/추가/삭제 → 수정 → 새로운 술 추천 → 비교 → 원본 위치 → 수정 후 재추천. 작은 화면·safe area·키보드·폰트 확대·사진 권한 거부·네트워크 끊김·AI timeout을 포함한다.

멘토 데모는 실제 저장과 실제 AI 호출 여부를 명시한다. 카탈로그가 제한되어 있으면 지원 범위를 공개하고 그 밖의 제품은 확인 필요로 둔다. Expo Go만 실행한 결과를 양 플랫폼 네이티브 검증으로 기록하지 않는다.

## 노트 v2

`npm run check`는 조건부 색·향 변화·향 계열 해제/복원, 8개 조합의 전체 skip, 모름/없음/강도 0, draft 소유자/버전 검증, SQL 카탈로그 snapshot 일치와 노트 RPC의 권한·중복·낡은 revision·원문 보존을 확인한다. CI의 disposable Supabase HTTP 테스트는 실제 SDK로 기본 기록→노트 RPC→재시도→타 계정 읽기 차단을 수행한다. 개발 cloud 계정/키를 사용하지 않는다.

iOS 개발 빌드의 `/dev/tasting?category=wine&mode=deep&question=appearance`는 __DEV__에서만 열린다. 개발용 배너를 표시하고 Auth/저장 요청을 보내지 않는다. 실제 사용자 흐름의 로그인 검증을 대체하지 않는다. [네이티브 확인과 남은 항목](verification/tasting-notes.md)을 구분해서 보고한다.

## 메뉴 추천 응답·품질 회귀

`npm run test:menu-quality`는 4주종 × 가볍게/자세히 합성 관측, 취향 근거 제외 조건, 카탈로그 판본 및 조작된 추천 응답 거부를 검사한다. 정상 서버 응답은 실제 HTTP CI에서도 같은 validator로 확인한다. [실측·추정·개발 전용 확인과 남은 범위](verification/menu-quality.md)를 구분한다.

메뉴 제외 회귀는 `tests/menu-review.test.ts`에서 재분석·사진 추가·원문 변경·재촬영·수동 입력·일시적 OCR 실패·JSON 복구를 검사한다. iOS 실제 종료/재실행 확인과 기기별 동기화 한계는 메뉴 검증 문서를 참조한다.

메뉴 복구 회귀는 `tests/menu-restore.test.ts`에서 실제 빈 저장과 읽기 실패, JSON/계정 경로/원문 참조, 카탈로그 변경 뒤 pendingSave 보존을 검사한다. 저장 transport의 opaque ID가 추천 권한으로 사용되지 않는지는 실제 HTTP CI에서 저장/재전송 성공·추천 거부로 검증한다. iOS 읽기 실패→재시도와 Android 도구 제약은 [메뉴 복구](verification/menu-recovery.md)에 구분했다.

추천 근거 링크/최신 상태는 `tests/menu-evidence.test.ts`와 실제 HTTP CI에서 확인한다. 주기·재진입 갱신과 미검증된 실제 장시간 기기 시나리오는 [근거 갱신](verification/menu-evidence-freshness.md)에 구분한다.

네이티브 OCR 검증 경로와 합성 14종 원문/좌표 baseline은 [실행 보고서](verification/native-ocr-benchmark.md)에 있다. `tests/ocr-benchmark.test.ts`는 지표 계산과 fixture 연결만 검증하며 네이티브 엔진을 mock 성공으로 대체하지 않는다. 실제 실행은 개발 빌드/로컬 fixture 서버가 필요하다.
