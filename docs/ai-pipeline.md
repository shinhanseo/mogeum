# AI 취향 요약·메뉴판 분석·추천

## 책임 분리

기본 방향은 **앱에서 OCR, 서버에서 메뉴 해석·제품 확인·최종 추천**이다. ONNX는 실행 런타임 후보이며 OCR 모델 자체가 아니다. 한글/영문 탐지·인식 모델, 전처리, decoding, 라이선스, 실행기 호환성까지 확인한 뒤 채택한다. ONNX와 ML Kit를 동일한 OcrAdapter 계약 뒤에서 비교한다. 엔진 선정을 이유로 출시 필수 기능을 무기한 미루지 않고 측정 결과에 따라 좁은 변경을 제안한다.

## A. 취향 요약

1. 서버가 해당 사용자의 현재 기록 revision을 확인한다.
2. 사진만 있거나 평가가 없는 기록을 맛 선호 분석에서 제외한다. 지각한 특징, 그 특징에 대한 선호, 전체 재음용 의사를 구분한다.
3. 코드로 주종별 특징·반복 선호·상반된 평가·근거 record ID를 집계한다. 동일 제품 반복 기록과 제품 다양성을 별도 고려한다.
4. AI에는 집계와 필요한 메모만 전달하고 claim별 근거를 붙인 구조화 결과를 받는다.
5. schema·소유권·근거 존재·삭제/수정 revision을 검사하고 저장한다.
6. 앱은 캐시된 요약을 보여주고 입력이 바뀌면 갱신 중/오래된 상태를 구분한다.

초기 1–2개는 기록별 발견, 충분한 기록은 반복 경향을 설명한다. 향의 달콤함을 실제 맛의 단맛 선호로 바꾸지 않는다. 기록 수가 적거나 애매하면 생략·불확실성을 표현하고 성격 유형처럼 확정하지 않는다.

## B. 여러 장 메뉴판

1. 앱에서 최대 5장 선택, EXIF 회전 정리·메모리 예산 내 resize, 사진별 업로드/로컬 draft 보존.
2. 사진별 OCR 수행. 순차 또는 제한된 동시 처리로 구형 기기 메모리를 제어한다. 취소·실패·재시도는 해당 사진만 영향.
3. 텍스트·line ID·사진 ID·이미지 버전·좌표를 서버에 보낸다. 입력 계약은 docs/api-contracts.md.
4. 서버가 열·줄·제목 관계를 이용해 이름·가격·용량·주종을 구조화한다. 없는 값은 null로 남긴다.
5. 겹친 메뉴를 판매 항목 기준으로 정리하고 모든 원본 출처를 유지한다. 이름이 같아도 잔/보틀은 분리한다.
6. 사용자 확인·수정. 변경 사항과 원 OCR을 구분하고 수정된 값을 이후 처리의 기준으로 삼는다.
7. 앱 재실행 시 세션·사진별 상태와 부분 결과를 복구한다. 사진 추가/삭제/재촬영은 revision을 바꾸고 이전 추천을 stale로 둔다.

서버 비전 fallback은 기본 경로가 아니다. 필요성·비용·사진 전송 UI를 결정한 경우에만 추가한다. 실패를 숨기기 위해 모든 사진을 자동으로 외부 모델에 보내지 않는다. 사용자 메뉴의 인젝션 문구는 명령이 아니라 데이터로 처리한다.

## C. 새로운 술 추천

1. 메뉴 항목을 정식 제품·생산자·연식/판본과 매칭한다. 이름/별칭 검색과 확인 상태를 저장한다.
2. 제조사 등 허용된 출처에서 제품 특징을 확인한다. source URL, 조회일, 제품 판본, 검증 상태를 저장한다. 제한된 초기 카탈로그로 시작해도 되지만 지원하지 않는 제품을 지원하는 척하지 않는다.
3. 사용자 기록의 선호 특징과 제품 특징을 같은 분류 체계로 정규화한다. 출처와 원문은 보존한다.
4. 서버의 명시적인 비교 로직으로 닮은 점, 다른 점, 불명확한 점을 산출한다. 후보는 실제 menu_item ID 집합으로 제한한다.
5. AI는 비교 결과에 근거해 짧은 설명을 작성한다. 자유롭게 메뉴나 특징을 생성하지 않는다.
6. 앱에 새로운 술/익숙한 술/제품 확인 후보를 구분해 표시한다. 제품 사진이 없으면 주종별 SVG.
7. 추천 → 비교 → 내 기록 근거 → 원본 메뉴판 위치 → 돌아가기 연결.

예: 글렌리벳 12년의 과일 계열 향을 사용자가 좋게 남긴 과일 향과 연결한다. 마무리는 크리미하고 부드러운 설명이며 사용자의 깔끔한 끝맛 선호와 **같다고 주장하지 않는다**. 공식 출처: https://www.theglenlivet.com/en/whisky/12-year-old-single-malt-scotch/ . 메뉴 이름·가격과 사용자 기록은 디자인용 예시이므로 운영 제품 카탈로그와 사용자 데이터로 대체해야 한다.

## 비용·실패·평가

동일 입력 hash/revision은 재사용하고 탭 진입마다 모델을 호출하지 않는다. 서버에서 사용자별 호출 한도, 동시 처리 수, timeout, 제한된 retry/backoff, 모델·프롬프트 버전을 기록한다. 로그에는 사진·개인 메모·키를 기본 출력하지 않는다.

OCR 성능은 엔진명이 아니라 실제 20–30장 테스트의 이름 인식, 가격/용량 연결, 한국어/영문 혼용, 저조도, 기울어짐, 열 배치, 구형 기기 메모리/지연으로 결정한다. AI는 존재하지 않는 메뉴 추천, 근거 없는 맛/선호 주장, 이미 수정된 기록 인용, 불확실 제품 강제 매칭, prompt injection 저항을 평가한다. 평가셋은 허가된 메뉴판 또는 합성 데이터만 Public 레포에 넣는다.

## 현재 노트 문장 정리와 AI 근거의 경계

현재 질문 노트의 composeNote는 결정적 템플릿이다. 선택된 계열만으로 세부 향을 확장하지 않으며, 건너뛴 값과 숨겨진 색·향 변화·세부 향은 serializeAnswers에서 제외한다. LLM 호출 없이도 미리보기와 직접 수정을 사용할 수 있다.

취향 분석 구현 시 record_notes의 현재 mode/catalog_version에 해당하는 답변만 읽고 confirmed_input_revision과 input_revision이 일치하는 확정 상태인지 확인한다. 사용자 원문을 제품의 객관적 특징이나 특정 향 선호로 승격하지 않는다. 비활성 모드·삭제된 계열·사진뿐인 기록은 감각 근거가 아니다. 분석 서버는 이 판정과 RLS/JWT 검증을 별도로 구현해야 하며, 현재 노트 화면 구현이 AI 요약 완료를 뜻하지 않는다.
